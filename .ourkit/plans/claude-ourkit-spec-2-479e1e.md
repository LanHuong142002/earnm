# Plan: People can create an account and sign in on iPhone

Spec: `.ourkit/specs/claude-ourkit-spec-2-479e1e.md` (ticket #2). Tier: Feature. Sensitive Areas: auth, data, schema, public API.

## Approach

Build email and password auth ourselves in the Express API, from Node's built-in `crypto` plus `zod` for input checks. Prisma stores two tables, `User` and `Session`. Sessions are opaque random tokens. Only their SHA-256 hash is stored, and they expire 90 days after last use. Passwords are hashed with `crypto.scrypt`. Failed sign-ins are counted in memory, per email and per IP. All errors go through one handler that returns `{ error: { code, message } }`. The app is built by a `createApp({ prisma, now })` factory, so tests can use a test database and a controllable clock.

On the phone, an `AuthProvider` keeps the session token in `expo-secure-store` (the iOS Keychain) and guards routes with Expo Router's `Stack.Protected`. It talks to the API through one small `fetch` client. Text comes from `i18next` with `vi` and `en` files. The language is the account's saved choice if there is one, otherwise the phone's language from `expo-localization`.

The user chose this hand-built approach over Better Auth, because Better Auth doesn't meet R8, R12 and R13 as they stand (see Prior Art). They also chose a local PostgreSQL for tests.

## Prior Art

- **In the project:** nothing to reuse. The API has only `GET /health`. The Prisma schema has no models or migrations. The app has a placeholder screen with no API client, secure storage or translations.
- **Better Auth 1.7.18** (with `@better-auth/expo`): supports Express 5, Prisma 7, email and password, database sessions, Google later, and an Expo client. **Not reused.**
  - Its docs don't say the session token is hashed in the database (R8).
  - Its rate limit is per IP only, so a per-email limit would be custom code anyway (R12).
  - Its error shape differs from R13.
  - It adds four tables.
  - Its Expo docs target SDK 55, not 58.
  - Bending it to the spec would cost about as much code as writing auth, with more unknowns.
- **Password hashing:** Node's built-in `crypto.scrypt` is used rather than `argon2` or `bcrypt`. It needs no native build on Windows or Render and is a memory-hard function. Better Auth uses the same.
- **Reused libraries:**
  - API: `zod` 4 for validation, `@prisma/adapter-pg` (the Postgres driver adapter that Prisma 7's `prisma-client` generator needs), and `vitest` with `supertest` for tests.
  - Phone: `expo-secure-store` and `expo-localization`, installed with `npx expo install` so they match SDK 58, plus `i18next` with `react-i18next`. Node 24 is installed, which meets i18next's requirement of Node 22 or later.
- **Rate limiting:** `express-rate-limit` isn't used. It counts requests, not failed attempts per email, so a small in-memory counter is simpler and testable with the injected clock.
- **Google sign-in later:** it will add an `OAuthAccount` table (provider, provider user id, `userId`) and make `User.passwordHash` optional. Neither change reworks existing accounts, so nothing extra is built now.

## Changes

### API (`apps/api`)

- **Dependencies:** add `zod` and `@prisma/adapter-pg`, plus dev dependencies `vitest`, `supertest` and `@types/supertest`. Add the scripts `test` (`vitest run`), `db:migrate` (`prisma migrate dev --config prisma7.config.ts`) and `db:deploy`.
- **`prisma/schema.prisma`:**
  - `enum Language { vi en }`.
  - `User`: `id` (uuid), `email` (unique, stored lowercase), `passwordHash`, `displayName`, `language Language?` (null means follow the phone), `createdAt`, `updatedAt`.
  - `Session`: `id`, `tokenHash` (unique), `userId` (foreign key to `User`, delete cascade, indexed), `createdAt`, `lastUsedAt`.
- **`prisma/migrations/<timestamp>_auth/migration.sql`:** generated by `prisma migrate dev` and committed. It applies to an empty database (R27).
- **`.env.example`:** `DATABASE_URL`, `TEST_DATABASE_URL` and `PORT`, with placeholder values (R28).
- **`src/db.ts`:** builds a `PrismaClient` with the `pg` adapter from a connection string.
- **`src/app.ts`:** `createApp({ prisma, now })` sets `trust proxy` to 1 for Render, JSON body parsing with a 10 kB limit, the routes, a 404 handler and the error handler. **`src/index.ts`** only creates the app and listens.
- **`src/http/errors.ts`:**
  - An `AppError(status, code)` class and the error middleware.
  - The middleware maps `zod` errors to `400 validation_failed` with the failing field names, and malformed JSON to `400 invalid_json`.
  - Anything unexpected becomes `500 internal_error` with a generic message. Only the error name and stack go to the server log, never request bodies (R13, R3).
- **`src/auth/password.ts`:**
  - `hashPassword` uses scrypt with a 16-byte random salt and stores the parameters with the hash. `verifyPassword` compares with `timingSafeEqual`.
  - `dummyVerify` runs a verify for unknown emails, so both failures take similar time (R3, R7).
- **`src/auth/sessions.ts`:**
  - `createSession` makes a 32-byte `randomBytes` token encoded base64url, and stores its SHA-256 hash.
  - `resolveSession` finds by hash and rejects if `lastUsedAt + 90 days <= now`. Otherwise it updates `lastUsedAt` when it's more than an hour old, so not every request writes.
  - `revokeSession` deletes the session (R8, R9, R11).
- **`src/auth/rate-limit.ts`:** an in-memory failed-attempt counter keyed by email (5 per 15 minutes) and by IP (20 per 15 minutes). It uses the injected `now()` and drops expired entries as it goes (R12).
- **`src/auth/require-auth.ts`:** middleware that reads `Authorization: Bearer <token>`, resolves the session, and refuses with `401 not_signed_in` (R10).
- **`src/auth/routes.ts`:**
  - `POST /auth/sign-up` validates email, password and name, and creates the user and a session. A unique-constraint error (Prisma `P2002`) becomes `409 email_in_use`, which also covers two sign-ups at once (R1–R6).
  - `POST /auth/sign-in` checks the limit first, then credentials. Unknown email and wrong password both give `401 invalid_credentials` and count as failures. A limited request gets `429 too_many_attempts` (R7, R12).
  - `POST /auth/sign-out` requires auth and deletes the current session (R11).
  - Both sign-up and sign-in return `{ token, user }`.
- **`src/me/routes.ts`:**
  - `GET /me` returns `{ id, email, displayName, language }` (R14).
  - `PATCH /me` accepts `{ language: "vi" | "en" }` and returns the updated profile (R24).
- **Tests:** in `src/**/*.test.ts`, with `vitest.config.ts`. A global setup reads `TEST_DATABASE_URL`. It **refuses to run** if that's missing or equal to `DATABASE_URL`, applies migrations, and the tests truncate the tables before each test.

### Phone (`apps/mobile`)

- **Dependencies:** `npx expo install expo-secure-store expo-localization`, then `i18next` and `react-i18next`. Also add the dev dependency `eslint-plugin-i18next` with its `no-literal-string` rule on JSX text (R22).
- **`.env.example`:** `EXPO_PUBLIC_API_URL`, the PC's LAN address such as `http://192.168.1.10:3000`, since the iPhone can't reach `localhost`.
- **`src/lib/api.ts`:** a `fetch` wrapper. It adds the bearer token, parses the error shape into an `ApiError(code)`, and turns network failures into `ApiError("network")`.
- **`src/auth/token-store.ts`:** reads, saves and deletes the token, plus the last known language choice, in `expo-secure-store` (R16).
- **`src/auth/AuthProvider.tsx`:** a context holding `status` (`loading`, `signedIn` or `signedOut`), the profile, `signIn`, `signUp`, `signOut` and `setLanguage`.
  - On launch, a stored token means signed in straight away (R15). The profile is then refreshed in the background.
  - `not_signed_in` clears the token and signs out (R17). A network error keeps the person signed in (R18).
  - `signOut` clears local state even if the server call fails (R20).
- **`src/i18n/index.ts`, `vi.json`, `en.json`:** all strings for these screens, including one message per error code. The language is the saved account choice if there is one, otherwise `vi` when the phone's first language is Vietnamese, otherwise `en`. It updates when the choice changes (R22–R26).
- **Routes:**
  - `src/app/_layout.tsx` wraps the app in `AuthProvider` and the i18n provider, and uses `Stack.Protected` to show the auth or app group.
  - `src/app/(auth)/sign-in.tsx` and `sign-up.tsx` show inline error text and a disabled submit button while sending, and clear the password after a failure (R19).
  - `src/app/(app)/index.tsx` is a simple signed-in home that links to Settings. `src/app/(app)/settings.tsx` has a VI/EN choice and a sign-out button.
  - Everything is laid out as compact vertical forms with no tables (R21).
  - The placeholder `src/app/index.tsx` moves into `(app)`.
- **Design (R21), added after `DESIGN.md` was agreed:**
  - `src/theme/tokens.ts` holds the light and dark colours, type, spacing, radius and motion from `DESIGN.md`. `src/theme/useTheme.ts` picks the set from `useColorScheme()`.
  - Plus Jakarta Sans (weights 400, 600 and 800) is bundled through `@expo-google-fonts/plus-jakarta-sans` and loaded with `expo-font` in `_layout.tsx`, while the splash screen stays up.
  - Small shared components in `src/ui/`: `Screen`, `Button`, `TextField`, `Card`, `ChoiceRow`, `ErrorText` and `Pressable` with press scale. Entrance, press and shake motion use `react-native-reanimated` and respect Reduce Motion through `useReducedMotion()`.
  - The four screens are rewritten on these components, with no hard-coded colours or sizes.
  - The `app.json` splash background changes from `#208AEF` to the theme background.

### Project

- **`.ourkit/stack-profile.json`:** set `commands.test` to `npm --prefix apps/api test`, so the test Gate runs.

## Risks

- **Sensitive Areas: auth, data, schema and public API.** A separate Sensitive Reviewer checks them at Review.
- **Account enumeration.** Sign-up deliberately reveals "email in use" (R5, accepted at Spec). Sign-in doesn't: it gives the same error and a similar delay through `dummyVerify`.
- **Rate limits live in memory.** They reset on restart and don't work across several processes. That's acceptable on one Render instance. If the API ever scales out, the limit must move to a shared store.
- **Client IP behind Render's proxy.** Without `trust proxy`, every request shares one IP and the IP limit would lock everyone out. It's set to 1 hop, and a test checks the limit uses `X-Forwarded-For`.
- **Session secrets.** Tokens never reach logs. Only hashes are stored, and the token is compared through a lookup by its hash.
- **Prisma 7 with the new generator and driver adapter.** It's new, so the first task generates the client and runs the first migration before anything else depends on it.
- **Tests wiping real data.** The test setup refuses to run without a separate `TEST_DATABASE_URL`.
- **Running on the iPhone.** Expo Go reaches the API only over the LAN, through `EXPO_PUBLIC_API_URL`, and plain `http` must work in Expo Go. If it doesn't, the Test Handoff notes a tunnel instead.
- **Your setup step.** There's no PostgreSQL on your machine yet. You'll need to install one and create a test database before the test Gate can run. This goes into `ourkit pending`.
- **Font package.** `@expo-google-fonts/plus-jakarta-sans` is maintained by the Expo team. The font files ship inside the app, so nothing loads from the web at run time. Vietnamese diacritics must render correctly, which goes in the Test Handoff.
- **New dependencies:** `@expo-google-fonts/plus-jakarta-sans`, `zod`, `@prisma/adapter-pg`, `vitest`, `supertest`, `expo-secure-store`, `expo-localization`, `i18next`, `react-i18next` and `eslint-plugin-i18next`. All are widely used and well maintained. Approving this plan approves adding them.

## Test Strategy

The project has no test command today. This plan adds `vitest` and sets `commands.test` in the Stack Profile, so tests run through `ourkit gate run test`. Until you install PostgreSQL locally and set `TEST_DATABASE_URL`, the API tests can't run. The Gate will report them as not run, never as passed.

- **API tests with `supertest` against `createApp`, a real test Postgres and an injected clock:**
  - **R1–R4:** valid sign-up; each invalid field rejected with its name; email normalised; stored hash not equal to the password and verifying only with it. A spy on the logger checks that the password never appears in logs.
  - **R5:** duplicate email in another case gives `409`. Two parallel sign-ups give exactly one user.
  - **R6–R8:** both sign-up and sign-in return a token that works on `GET /me`. The stored `tokenHash` isn't the token. Unknown email and wrong password give identical responses.
  - **R9:** clock moved 90 days plus 1 ms means refused. Used on day 89, the token still works on day 178.
  - **R10:** no token, a random token and an expired token each give `401 not_signed_in`.
  - **R11:** after sign-out, that token is refused, while a second session for the same person still works.
  - **R12:** the 6th failure for one email gets `429`, even with the right password, and it works after 15 minutes. The 21st failure from one forwarded IP across emails gets `429`.
  - **R13:** every error matches the shape. A forced internal error returns a generic message without a stack.
  - **R14, R24:** `GET /me` returns exactly four fields. `PATCH /me` saves the language and rejects other values.
  - **R25:** a new user's `language` is `null`.
  - **R27:** the global setup applies the migrations to the empty test database on every run.
- **Unit tests:** `password.ts` (round trip, wrong password, tampered hash) and `rate-limit.ts` (window edges).
- **Lint (`ourkit gate run lint`):** the `i18next/no-literal-string` rule fails on hard-coded JSX text in the mobile app (R22).
- **Build (`ourkit gate run build`):** the API type-checks.
- **Test Handoff (iPhone with Expo Go, cannot be automated here):**
  - R15–R20: sign up, kill and reopen the app (still signed in), sign out, sign in again; sign out on another device and reopen (back to sign-in); Airplane mode and reopen (still signed in); trigger each error message; double-tap submit sends one request.
  - R21: compact vertical layout that matches `DESIGN.md` in light and dark mode on an iPhone SE-sized and a Pro Max-sized screen; Vietnamese diacritics render in Plus Jakarta Sans; with Reduce Motion on, screens only fade. Review also checks that no component hard-codes colours or sizes.
  - R23–R26: phone set to Vietnamese or French before sign-in; choose English in Settings; the choice applies on a second phone set to Vietnamese.
  - Code review confirms the token is written only through `expo-secure-store` (R16).
- **R28:** checked in review. `.env.example` exists with placeholders, and `git check-ignore` shows `.env` is ignored.
