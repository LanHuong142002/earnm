# Plan: Members can track tasks in a simple list

Spec: `.ourkit/specs/claude-ourkit-spec-6-block-check-e6ffdc.md` (ticket #6). Tier: Feature. Sensitive Areas: data, schema, public API.

## Approach

API: add `Task` and `TaskAssignee` in one additive migration, and a tasks router nested under a project (`/projects/:projectId/tasks`). It follows the projects router: `requireAuth`, a membership lookup that gives the same `404` for "not a member" and "doesn't exist", strict zod schemas, an idempotent create on the phone-chosen id, and per-field last-write-wins through the existing `applyLastWriteWins`. Assignees and the due date are each one LWW field. Their writes are custom steps inside the same transaction: the conditional `updateMany` claims the field's time, and the assignee rows are replaced only if it matched.

Mobile: tasks share the **one** write queue the projects provider already owns, so a task created offline in a project created offline is always sent after its project. The queue gets per-entity result handlers. Today it has one `onApplied`/`onRejected` for the whole queue, and those know only projects. Everything else for tasks is a parallel, React-free set in `src/tasks/` modelled on `src/projects/`: api, sync senders, store with overlay, outcomes and sync cycle. A `TasksProvider` sits under `ProjectsProvider`, and pure modules handle ordering, filters, "due soon" and date formatting. Screens are new routes under `projects/[id]/tasks/`, registered in the Home stack, following the spec's navigation map (requirement 21).

The member list (requirement 8) is one isolated task that comes last and starts only after the user confirms #5 is done (see Risks).

- **Reused as templates, written again for tasks:** `projects/sync.ts`, `store.ts` (`applyOverlay`, cache load, save and clear with the owner check), `outcomes.ts`, `optimistic.ts`, `syncCycle.ts`.
  - Making them generic now would mean editing working, tested #4 code that #5's session is also likely to touch. A copy specialised for tasks is about 300 lines and keeps the two features apart. Extracting a generic version is a later refactor, once a third entity shows what is truly shared.
- **The one change to shared code:** `createQueue`'s single `onApplied`/`onRejected` becomes a dispatch by `change.entity`. `registerEntity` takes optional `{ onApplied, onRejected }` with the senders, and the queue-level handlers stay as the fallback, so projects behave exactly as before. Without this, the projects handlers would receive task results.
- **Date picker:** `@expo/ui` is already installed and unused, and has a native date and time picker. At Build, check the SDK 58 docs to confirm it runs in Expo Go.
  - If it does, use it, with no new dependency.
  - If not, `npx expo install @react-native-community/datetimepicker`, which the user already accepted at Spec and which ships in Expo Go.
- **Date formatting and "due soon":** written by hand as pure functions, like `formatMoney`, so the output doesn't depend on Hermes's Intl data. There is no date library in the app, and one isn't needed for whole days.
- **No chips, switch, action sheet or avatar component exists.**
  - Filters use a small new `FilterBar`: status as selectable pills, where the selected one shows a check (not colour alone, per DESIGN.md), and React Native `Switch` for "My tasks" and "Due soon".
  - Picking a status in one tap uses `ActionSheetIOS` (the app runs on iPhone), with `Alert` buttons on other platforms.
  - Assignees show as first names ("Lan, Huy +2"), because DESIGN.md rules out initials avatars.

## Changes

### API (`apps/api`)
- `prisma/schema.prisma`:
  - Add `enum TaskStatus { todo doing done }`.
  - Add `Task`:
    - `id String @id` (the phone supplies it), `projectId` (FK, `onDelete: Cascade`, `@@index`).
    - `title`, `description @default("")`, `status @default(todo)`, `dueDate DateTime? @db.Date`, `dueTime String?` (`HH:mm`).
    - `titleEditedAt`, `descriptionEditedAt`, `statusEditedAt`, `dueEditedAt`, `assigneesEditedAt`.
    - `createdById String?` (FK to `User`, `onDelete: SetNull`), `createdAt`, `updatedAt`.
  - Add `TaskAssignee { taskId, userId, @@id([taskId, userId]), @@index([userId]) }`, with both FKs `onDelete: Cascade`.
  - Add back-relations on `User` and `Project`.
- `prisma/migrations/<timestamp>_tasks/`: generated by `db:migrate`. It only adds tables.
- `src/tasks/routes.ts` (new): `createTasksRouter(deps)`, `Router({ mergeParams: true })`, mounted at `/projects/:projectId/tasks` in `src/app.ts`.
  - **Every route** checks `projectId` is a uuid and the caller is a member (`findForMember`, reused from projects). Otherwise it gives `404 not_found` with the same body (R9).
  - **Task shape:** `{ id, projectId, title, description, status, dueDate: "YYYY-MM-DD"|null, dueTime: "HH:mm"|null, assignees: [{ id, displayName }], createdById, createdAt }`.
  - **`GET /`:** that project's tasks with their assignees, in one query with `include`.
  - **`POST /`:** body `{ id, title, description?, status?, dueDate?, dueTime?, assigneeIds?, editedAt }`, strict.
    - In a transaction: a task with this id in this project gives `200`. The id used anywhere else gives `409 id_conflict`.
    - Otherwise check that every assignee is a member of the project (R3), then create the task with all `*EditedAt` set to the clamped time, `createdById` = the caller, and the assignee rows, giving `201`.
    - On P2002, run the transaction once more, as projects do.
  - **`PATCH /:taskId`:** body `{ fields: { title?|description?|status?|due?|assignees?: { value, editedAt } } }`, strict, at least one field. `due.value` is `{ date, time } | null`; `assignees.value` is a list of user ids.
    - The task must be in this project, or `404`.
    - In one transaction, `applyLastWriteWins` with a `write` that maps:
      - `due` → `dueDate` and `dueTime`;
      - `assignees` → `updateMany` claiming `assigneesEditedAt`, then, only if `count === 1`, check membership, `deleteMany` and `createMany` the rows.
    - A non-member assignee throws `400 validation_failed`, so the whole transaction rolls back.
    - Returns the current task with `200` (R13).
  - **`DELETE /:taskId`:** `404` if the task isn't in this project. `403 forbidden` unless the caller created it or is an Owner (a task with no creator: Owner only). Then `deleteMany`, giving `204`.
  - **Validation:**
    - title trimmed, 1–120 characters; description trimmed, ≤2000;
    - status enum; `dueDate` a real calendar date; `dueTime` `HH:mm` (00–23 and 00–59) and only with a date;
    - `assigneeIds` uuids, unique, ≤20.
  - **Body size:** the existing 10kb body limit covers the largest valid body (2000 characters plus 20 ids).
- `src/app.ts`: mount the router.
- `src/test/helpers.ts`: tasks are emptied by the existing `TRUNCATE "Project" ... CASCADE`, so nothing is needed there. Add a small `addMember(projectId, userId, role)` for tests (direct insert), because #5 isn't merged.
- **Gated, last task:** `GET /projects/:projectId/members` returning `[{ id, displayName, role }]`. Before starting it, ask the user whether #5 is done. If #5's endpoint exists, use it and drop this one.

### Mobile (`apps/mobile`)
- `src/sync/queue.ts`: `registerEntity(entity, senders, handlers?)` with optional per-entity `onApplied`/`onRejected`, used before the queue-level ones. Covered by tests: a project change still reaches the old handlers, and a task change reaches only the task handlers.
- `src/projects/ProjectsProvider.tsx`: expose the queue (and its `afterEnqueue` flush) through context, so tasks enqueue into it. This is the only change there.
- `src/tasks/` (new):
  - `api.ts`: `listTasks`, `createTask`, `patchTask`, `deleteTask`.
  - `sync.ts`: `registerTaskEntity(queue, handlers)`. Changes use entity `"task"`, with `data` holding the `projectId`.
  - `store.ts`:

    - `validateTaskInput`, with the server's limits.
  - `outcomes.ts`:

  - `syncCycle.ts`: `refresh(projectId)` (GET, then overlay, then save), React-free and injectable, like `projects/syncCycle.ts`.
  - `optimistic.ts`: `planTaskUpdate` (send only touched fields, each with its time).
  - `TasksProvider.tsx`, placed under `ProjectsProvider` in `src/app/_layout.tsx`:

    - registers a sign-out cleanup that clears the cache and filters (R19);
    - drops cached task lists for projects no longer in the project list.
  - `listOrder.ts`: sort and group (R22).
  - `filters.ts`: status, mine and due soon, combined (R24).
  - `dueDate.ts`:
    - `isDueSoon(task, now)` and `isOverdue(task, now)` (R25: due before the end of today + 3 days; a date without a time means the end of that day);
    - `formatDue(date, time, lang)`, for example `T6, 14/11 · 14:30` and `Fri, 14 Nov · 14:30`.
  - `permissions.ts`: `canDeleteTask(task, me, role)`.
  - Components: `TaskCard` (title, status pill that opens the status picker, assignee names, due date and an "Overdue" word), `FilterBar`, `TaskForm`, `StatusPicker` (`ActionSheetIOS`/`Alert`), `TaskRejectedNotice`, and `DueField` (the date picker wrapper).
- Routes in `src/app/(app)/(home)/projects/[id]/tasks/`: `index.tsx` (Task list), `new.tsx`, `[taskId]/index.tsx` (Task details) and `[taskId]/edit.tsx`. All are registered in `(home)/_layout.tsx`. Moves:

  - list → task and task → edit are `push`; saving the edit does `back()`;
  - delete does `dismissTo` the task list;
  - a task that vanished navigates to the list.
- `projects/[id]/index.tsx`: one "Tasks" row (a `Card` row with the not-done count from the cache, or no count when that project's tasks were never loaded), between the details and Edit. The Project screen refreshes its tasks on focus, so the count appears after one online visit.
- `src/i18n/en.json`, `vi.json`: a `tasks.*` section (statuses, filters, empty states, overdue, notices, form labels and errors, weekday and month names for `formatDue`).
- **Assignee picker (part of the gated task):**
  - `TaskForm`'s assignee field uses `ChoiceRow`s from the member list (from #5's endpoint or ours), cached per project for offline use (R27).
  - Until then, the form doesn't show the assignee field, and existing assignees still show on cards.

## Risks

- **Sensitive Areas (data, schema, public API):**
  - Every task route must scope by project membership, and the task must belong to that project; otherwise one project's task could be read or changed through another project's URL. Tests cover cross-project ids on every route (AC 9). The Review runs `ourkit-sensitive-reviewer`.
  - Assignee validation runs inside the write transaction, so a non-member can never be stored.
- **Parallel work with #5:**
  - Both branches will touch `schema.prisma` (back-relations on `User`/`Project`), `app.ts`, possibly `ProjectsProvider.tsx`, and `en.json`/`vi.json`. Both migrations only add tables. Textual conflicts are expected and small; they are resolved when the second PR merges, in the session that owns it (lesson: merge only from the session that owns the change).
  - The member list is deferred to the last task, which stops and asks the user first, so the two features don't build two member endpoints.
- **Shared queue change:** the per-entity dispatch touches tested #4 code. Projects keep the queue-level handlers, and the existing `queue.test.ts` must pass unchanged, plus new dispatch tests.
- **Ordering across entities:** a task change for a project the server has refused or deleted gets `404`, is dropped with the notice, and the queue moves on (R18). It never stalls, because permanent refusals already continue.
- **Dates and time zones:** `@db.Date` comes back from Prisma as UTC midnight. The API serialises it with `toISOString().slice(0, 10)` and parses `YYYY-MM-DD` as UTC, with tests for a date near midnight. "Due soon" and "overdue" are worked out only on the phone, from the phone's clock and time zone.
- **Assignees LWW is a whole set:** concurrent edits keep the later set. The spec accepts this (Out of Scope).
- **Project screen density:** DESIGN.md allows three sections before the first scroll. The Tasks entry is a single row inside the existing flow, and the mockup will show it.
- **Date picker in Expo Go:** checked against the SDK 58 docs before use, with the agreed fallback.
- **Look (lesson):** before building the screens, show the user a mockup of the Task list (filters, cards, Done section), the Task form and the Project screen's Tasks row, and get approval.
- **Review convergence (lessons):**
  - Only correctness, security and spec gaps block. Nits are logged as non-blocking.
  - Reviewers run one after another on the shared test database.

## Test Strategy

Commands: `ourkit command test` (`npm --prefix apps/api test && npm --prefix apps/mobile test`; the mobile script runs `tsc --noEmit` first), `ourkit command lint` (mobile), `ourkit command build` (API).

- **API, vitest + supertest on the real test database** (AC 1–13, 29):
  - limits and defaults;
  - date and time validation, including a time without a date and a date near midnight;
  - assignee rules: non-member, duplicate, 21;
  - phone-chosen id, idempotent create, cross-project id conflict;
  - Member edits any field;
  - delete by creator and by Owner, `403` for others, `404` on a second delete;
  - list scoped to the project, with display names;
  - `404` with the same body for a non-member, a missing project and a cross-project task id, on every route;
  - `401` on every route;
  - cascades on project delete and user delete (`createdById` becomes null, after which only an Owner can delete);
  - per-field LWW: an older status is ignored while a newer title is accepted, a future time is clamped with `createClock`, the assignees set is replaced, and a fully ignored change returns `200`.
  - Second members are inserted with the `addMember` helper.
  - The migration is applied by the existing global setup (`migrate deploy`).
- **Mobile, vitest on pure modules** (AC 14, 16–18, 20, 22, 24, 25):
  - `applyTaskOverlay`: rename kept over a stale refresh, a missing task removed;
  - queue merging with task changes;
  - the per-entity dispatch;
  - outcomes for `403`/`404`/`401`;
  - a `404` for a deleted project dropped while the next change still sends;
  - list ordering and grouping;
  - each filter alone and combined;
  - `isDueSoon`/`isOverdue` with a fixed clock (yesterday, today, +3 days, +4 days, Done, no date, a date without a time);
  - `formatDue` in both languages;
  - `canDeleteTask`;
  - the cache owner check.
  - AC 20 is a code check: no `task` reference in `src/sync/`.
- **Network failures in tests (lesson, decided here):** fake senders that throw `ApiError("network")`, never real closed ports.
- **The member list (gated task):** an API test for AC 8 if we build the endpoint. If #5's endpoint is used, its own tests cover it, and a check here confirms the shape the picker needs.
- **By hand in Expo Go, becoming the Test Handoff** (AC 15, 17 by-hand part, 19, 21, 23, 26–28):
  - airplane mode and force-quit;
  - offline create, status change and delete, then reconnect;
  - sign out and switch person;
  - every move in the navigation map, with header back and swipe;
  - status change from a card;
  - filters remembered after a restart;
  - empty states;
  - the form: title only, field messages, date and time set and cleared, the keyboard, delete only for creator or Owner (a Member inserted by SQL until #5 merges);
  - both languages and DESIGN.md.
- **Not verified automatically:** the screens, the date picker, `ActionSheetIOS`, and real NetInfo and AppState triggers. These are covered by the Test Handoff.
