# Plan: Tasks can have checklists and colour labels

Spec: `.ourkit/specs/claude-ourkit-spec-7-checklists-labels.md` (ticket #7). Tier: Feature. Sensitive Areas: data, schema, public API. Mockup: `.ourkit/mockups/claude-ourkit-spec-7-checklists-labels.html`.

## Approach

API: one additive migration adds `Checklist`, `ChecklistItem`, `Label`, `TaskLabel` and `Task.labelsEditedAt`. Two new routers follow the #6 tasks router exactly: `requireAuth`, the same `404` for "not a member", "doesn't exist" and "belongs elsewhere", strict zod schemas with the shared `singleLineText`, the project row lock for every write (so limits and duplicate names are checked safely), idempotent create on the phone-chosen id, and per-field last-write-wins through `applyLastWriteWins`. A task's labels become one more set-valued field on the existing task `PATCH`, written the same way assignees are. Reading tasks returns label ids and checklists with items.

Case-insensitive unique label names use a stored `nameKey` (the name trimmed, NFC-normalised and lower-cased) with `@@unique([projectId, nameKey])`. The app checks first and gives a clear `409 label_name_taken`; the index catches a race. This needs no Postgres extension and matches how emails are normalised in `auth/routes.ts`.

Mobile: three new queue entities, `label`, `checklist` and `checklistItem`, registered from the tasks code like `task`, plus a `labels` field on task updates. Labels are cached per project beside tasks; checklists and items live inside each cached task, so the existing overlay and refresh carry them. Checklists are edited directly on the Task screen (no form). The label picker, the label filter and the new/edit label form are expo-router `formSheet` routes, so they open as native sheets with working back and swipe-down and no new dependency. The Labels screen is a normal pushed route.

## Prior Art

- **Reused as they are (API):** `applyLastWriteWins` (`http/last-write-wins.ts`), `singleLineText` (`http/text.ts`), `lockProject`, `findForMember` and `requireOwner` (`projects/access.ts`), `isUniqueViolation`, `AppError`, and test helpers `useTestApp`, `createClock`, `createSignedInUser`, `addMember`, `expectError`.
- **Copied as patterns (API):** the idempotent create with `id_conflict`, the limit check inside the transaction, and the assignee set write (claim `labelsEditedAt` with `updateMany`, then replace rows only if it matched). These are inline in `tasks/routes.ts`; extracting them now would mean changing #6's tested code for little gain. The two new routers keep the same shape so a later extraction stays easy.
- **Reused as they are (mobile):** the shared queue (`registerEntity`, per-entity handlers, `dropEntity`, merging by `entity` + `entityId`), `TasksProvider` and its cache and refresh, `ChoiceRow` (checkbox rows with a ✓), `Card`, `TextField`, `Button`, `PressableScale`, `OfflineNote`, `TaskRejectedNotice`, `Enter`, the `FilterBar` pills and `Switch` rows.
- **No sheet component exists.** Options: build one on reanimated and gesture-handler; add a bottom-sheet library; or use expo-router's `presentation: "formSheet"` with `sheetAllowedDetents`, which shows the native iOS sheet. Conclusion: use `formSheet`. It is native, already in the app's router, keeps navigation in one place (lesson: navigation map), and adds no dependency. At Build, confirm `sheetAllowedDetents` works in Expo Go for SDK 58; if not, fall back to `presentation: "modal"` with the same screens.
- **Contrast check:** no library. A small pure `contrastRatio(hexA, hexB)` (WCAG formula, about 15 lines) is enough for the AC 21 test.

## Changes

### API (`apps/api`)

- `prisma/schema.prisma`:
  - `enum LabelColour { gray red orange yellow green teal blue purple }`.
  - `Checklist { id String @id; taskId → Task (Cascade); name; nameEditedAt; createdAt @default(now()); items; @@index([taskId, createdAt]) }`.
  - `ChecklistItem { id String @id; checklistId → Checklist (Cascade); text; textEditedAt; done Boolean @default(false); doneEditedAt; createdAt @default(now()); @@index([checklistId, createdAt]) }`.
  - `Label { id String @id; projectId → Project (Cascade); name; nameKey; colour LabelColour; nameEditedAt; colourEditedAt; createdAt; tasks TaskLabel[]; @@unique([projectId, nameKey]) }`.
  - `TaskLabel { taskId → Task (Cascade); labelId → Label (Cascade); @@id([taskId, labelId]); @@index([labelId]) }`.
  - `Task` gains `labelsEditedAt DateTime` (the migration fills existing rows from `createdAt`), `checklists` and `labels` relations. `Project` gains `labels`.
- `prisma/migrations/<timestamp>_checklists_labels/`: generated by `db:migrate`, timestamp after `20261112060000_tasks` (lesson: order by merge). Only adds tables, one column and indexes.
- `src/tasks/routes.ts`:
  - The task response gains `labelIds: string[]` and `checklists: [{ id, name, createdAt, items: [{ id, text, done, createdAt }] }]`, ordered by `createdAt` then `id`, read with one `include`.
  - `PATCH` gains `fields.labels: { value: uuid[] (unique, ≤10), editedAt }`. In the transaction: claim `labelsEditedAt`; if claimed, check every id is a label of this project (otherwise `400 validation_failed`, rolling back), then replace the `TaskLabel` rows.
- `src/labels/routes.ts` (new), mounted at `/projects/:projectId/labels`:
  - `GET /` → `[{ id, name, colour }]` ordered by name.
  - `POST /` `{ id, name, colour, editedAt }`: under the project lock; same id in this project → `200`; elsewhere → `409 id_conflict`; 50 labels → `409 label_limit_reached`; same `nameKey` → `409 label_name_taken`; otherwise `201`. Retry once on P2002 for the id; a P2002 on the name index gives `label_name_taken`.
  - `PATCH /:labelId` `{ fields: { name?, colour? } }`: LWW per field; a rename checks `nameKey` against other labels first and gives `409 label_name_taken` (whole request rolled back). Returns the label as it now is.
  - `DELETE /:labelId`: `requireOwner` → `403 forbidden` for a Member; then delete (cascade removes `TaskLabel` rows) → `204`.
- `src/checklists/routes.ts` (new), mounted at `/projects/:projectId/tasks/:taskId/checklists`:
  - `POST /` `{ id, name, editedAt }`: the task must be in the project; 10 checklists → `409 checklist_limit_reached`; idempotent like tasks.
  - `PATCH /:checklistId` `{ fields: { name } }`, `DELETE /:checklistId` → `204`.
  - `POST /:checklistId/items` `{ id, text, editedAt }`: 50 items → `409 item_limit_reached`; idempotent.
  - `PATCH /:checklistId/items/:itemId` `{ fields: { text?, done? } }`, `DELETE /:checklistId/items/:itemId` → `204`.
  - Each change returns the changed checklist or item as it now is. Every id in the path must chain to the project, otherwise `404 not_found` with the same body (R10, R12).
- `src/app.ts`: mount both routers.
- `src/labels/nameKey.ts`: `nameKey(name)`, shared with tests.

## Risks

- **Sensitive Areas (data, schema, public API):**
  - Every new route must chain ids to the caller's project (label → project; item → checklist → task → project). Otherwise one project's data could be changed through another's URL. Tests cover a cross-project or cross-task id on every route (AC 10). The Review runs `ourkit-sensitive-reviewer`.
  - Owner-only label delete is enforced on the server with `requireOwner`, not only hidden on the phone.
  - Task labels are validated inside the write transaction, so a foreign label is never stored.
- **The migration on existing data:** `labelsEditedAt` is `NOT NULL`. The migration adds it with a default and backfills it from `createdAt`, and a test applies it to a database with tasks (AC 23).
- **Unicode label names:** lower-casing is done in JS with NFC normalisation, so "Pha chế" and "PHA CHẾ" collide. A test covers Vietnamese diacritics.
- **Offline ordering:**
  - A label or checklist created offline and then used is sent first, because the queue is FIFO.
  - Deleting a parent removes its children's waiting changes, so nothing is refused for a parent that is gone.
  - A remaining edge: another person deletes a checklist while I'm offline adding items. My item creates get `404`, are dropped, and the notice shows. That is the spec's R12/R15 behaviour.
- **Task response size:** a task can carry 10×50 items. The tasks list has at most 1000 tasks, so an extreme project could return a large list. Real projects are far smaller (Out of Scope of #6: no paging). The 10kb body limit applies only to requests, which stay small.
- **`formSheet` in Expo Go:** checked at Build, with `modal` as the fallback (see Prior Art).
- **Appearance override:** `Appearance.setColorScheme` must run before the first screen renders, or the screen flashes in the wrong theme. The stored value is read during the existing splash/loading step. At Build, check on iOS in Expo Go that native headers and `Alert` follow it.
- **Cache shape change:** bumping the key to `v2` avoids reading an old shape. A first open after the update refetches.
- **Review convergence (lessons):**
  - Only correctness, security and spec gaps block. Nits go to the report.
  - After the first round, review only the fix commits.
  - Reviewers run one after another on the shared test database.
- **Hand-testing (lessons):** run `db:deploy` on the dev database and start with `npm run dev:phone` from this checkout before phone QA.
