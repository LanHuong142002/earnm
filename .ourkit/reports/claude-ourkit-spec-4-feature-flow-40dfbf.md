## Summary

Projects with offline sync (#4): API with per-field last-write-wins already merged in #25; this finishes the phone screens (tabs, Home, connected navigation, restyle).
Why: hand testing showed screens that didn't connect (no back, no swipe-back), a keyboard hiding Save, and a look the user rejected; the spec was rewritten at QA with the user.
Verified: test gate on the final code (API 156, mobile tsc + 146), lint, nine review rounds ending with no blocking finding, and the user's hand test on iPhone.
Watch: navigation uses raw stack actions to reset to the list after delete, and any non-401 profile failure now counts as offline; both are only checked by hand.
Left: Member view on a device (needs a SQL member row), paging, write rate limit (#23), and the non-blocking findings listed below.

## Details

**Decisions made at QA with the user.** Home is the start screen with a tab bar (Home, Account), a current-project banner with currency, three area tiles (Ideas and Shared schedule marked Coming soon), and a "Your projects" section. Screens connect as a stack so back and swipe-back always work (spec R29, 29a, 29b). "Switch project" was removed. Delete sits apart from Save. Each project is its own card. The first restyle (coloured stripes, initials avatars, gradient) was rejected as looking generated; DESIGN.md now follows the user's reference: flat orange banner, soft tiles, project cards with a tinted cover, icon and currency pill, and it lists stripes and rainbow avatars under Avoid.

**Review.** The rounds found and fixed, among others: deleting from a project opened from Home left the deleted screen in history; the keyboard offset under headers; a cached project list from another account shown briefly after a 401 and account switch; an in-flight create of one account landing in the next account's list; a 5xx at launch leaving the app stuck loading or inviting someone with projects to create their first one; a form that sent unchanged fields and could revert another device's newer edit.

**Non-blocking findings left:** tapping the banner body doesn't open the project (only its button does); after a 403 a failed follow-up refresh can leave the refused value until the next full sync; the AuthProvider now treats any non-401 profile failure as offline and retries the profile on foreground (session handling, approved with the plan addendum); GET /projects isn't paged (out of scope); a delete answered 404 counts as done with no notice.

## Teach-back

- Q1c: what happens when a phone's clock runs a day ahead? Misunderstood: Thought only times much later than the server are blocked; actually any editedAt later than server now is capped to now (not rejected), so the change is still applied with the server's time.
- Q1d: why updateMany with a lt condition instead of read-then-write? Misunderstood: Didn't know where updateMany is, what it does, or what lt means; missed that the database compares and writes in one atomic step, which avoids the read-then-write race.
- Q2b: the same create sent again for an id the caller already owns Misunderstood: Thought the server rejects it as a duplicate; it returns 200 with the existing project (idempotent), so the queue can drop the change.
- Q2c: two identical creates arriving concurrently Misunderstood: Thought the slower one is blocked with an error; the slower one hits P2002 on the primary key, the server catches it, re-runs createOnce and returns 200.
- Q3b: what the queue does with a rename answered 404 because the project was deleted Misunderstood: Thought the queue keeps running with that answer; it treats 404 as a permanent rejection, removes the change, reports it via onRejected and moves on to the next change.
- Q3d: how a 401 differs Misunderstood: Assumed a refresh-token flow (get a new token and retry); this app has no refresh token: a 401 means the session is gone, the queue keeps the change, the app returns to sign-in, and the change is sent after the same person signs in again.
